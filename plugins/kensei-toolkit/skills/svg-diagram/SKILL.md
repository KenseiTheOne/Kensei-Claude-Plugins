# svg-diagram — a picture that explains, drawn as code

The result is a hand-built SVG (no Mermaid, no external renderer) that GitHub shows inline, plus
the small Python script that generates it, so the picture can be edited later by changing text.
Reference pictures in this style live in the owner's projects and are not shipped with the plugin:
`night-runner/docs/night-flow.svg` (a pipeline row) and `KenseiUnityMCP/docs/diagrams/how-it-works.svg`
(an architecture with a store and a special path). `example.py` here rebuilds the second one with
the kit, so it is the reference you can run.

Commands below use `python3`; on Windows use `python` or `py -3` instead.

## Steps

1. **Find the story before drawing.** Read the thing being explained (README section, code,
   design doc). Write down, for yourself:
   - the **3–6 nodes** (actors, components, stages) — more than 6 boxes stops being readable;
   - the **edges** and what travels on each (protocol, data, trigger);
   - the **one idea** the picture must make obvious (the thing that makes this project special) —
     it gets the dashed amber "magic" path and its own label;
   - **three takeaways** for the badge row (emoji + 2–4-word head + one short line).
   If the request is vague about content, propose this outline in one message before drawing.

2. **Pick a layout archetype.**
   - *Pipeline row* — stages left to right with arrows (a night of the runner, a build).
   - *Architecture row* — actor → middle → target with duplex protocol edges, a supporting store
     (file, DB, cache) below with who writes and who reads it, the special path as an arc above.
   - *Hub* — one central card with 3–5 satellites; use only if the story is "one thing, many users".
   Width is **960**; height 250–470 (title band ~110 px, row ~130 px, badges ~60 px).

3. **Write the generator** next to the SVG: by default `docs/diagrams/<name>.py`, writing
   `docs/diagrams/<name>.svg` (and `<name>.ru.svg` etc. — one file per README language, all from one
   `TEXT = {lang: {...}}` dict so the versions stay in sync). `--out <path>.svg` in the arguments
   sets the SVG path instead: the generator and the kit go into that folder, the language variants
   get `.ru.svg` etc. next to it, and the README's `img src` is that path relative to the README.
   Copy the kit and the example there, so the committed generator rebuilds the picture on any
   machine and after a plugin update (the kit is one stdlib-only file; it is committed with the
   generator):

   ```bash
   cp "${CLAUDE_SKILL_DIR}/diagram_kit.py" docs/diagrams/
   cp "${CLAUDE_SKILL_DIR}/example.py" docs/diagrams/<name>.py   # then rewrite TEXT and build()
   ```

   Kit API (`diagram_kit.py`): `Diagram(w, h)`, `.background(title, subtitle, glows=[(x, y, palette[, r])])`,
   `.card(x, y, w, h, palette, emoji, title, mono=..., line=...)`, `.duplex(x1, x2, y, top, bottom)`,
   `.arrow(x1, y1, x2, y2, ink, label=..., label_side=1)` (the label sits beside the line, off it
   along its normal; `label_side=-1` for the other side), `.curve(svg_path_d, "magic", label, at=(x, y))`,
   `.box(x, y, w, h, emoji, head, sub)`, `.badges(y, [(emoji, head, sub), ...], width=None)` (44 px
   pills; the default width is `min(300, (canvas w − 40 − gaps) / n)`, so 2–4 pills fit),
   `.text(...)`, `.save(path)`, then `finish()` once after the last `save()`; `render_png(svg, png)`.
   Minimum heights (the lines sit at fixed offsets): a card 80 px with a title only, 100 with
   `mono=`, 120 with `line=`; a box 24, or 40 with `sub`.
   Palettes: orange, violet, teal, indigo, emerald, amber, rose, sky, slate. Inks: those names,
   main, dim, magic, or a hex colour.

4. **Build and fix the warnings.** `python3 docs/diagrams/<name>.py --strict` builds every language,
   prints all warnings, then exits 1 if there were any. The kit estimates every string's width
   (SVG text never wraps) and reports text overflowing its card/pill/box/edge on either axis, a card
   too short for its lines, text or a card/box/pill off the canvas, and texts overlapping other
   texts. It does **not** check lines and curves: a label crossed by an arrow, or an arrow through
   a card, passes the check and is caught only in step 5. Fix every warning by shortening the words
   first, then by widening or moving boxes. Never silence a warning by dropping the check.

5. **Look at it.** Render each language: `python3 docs/diagrams/diagram_kit.py render docs/diagrams/*.svg`
   writes each PNG to the system temp dir and prints its path (from Python:
   `render_png(svg, Path(tempfile.gettempdir()) / "<name>.png")`). Read every PNG. The estimate is
   approximate; the eye is the real check. Look for: clipped or crowded text, a label crossed by a
   line, arrows pointing at the wrong edge, glow or sparks behind text, uneven spacing, a
   translation that ran longer than the English. Fix and render again until clean — usually 2–3
   rounds. Do not hand over a picture you have not looked at.
   The renderer is headless Chrome or Edge, found in the usual install places; `CHROME=<path>`
   points at another Chrome/Chromium/Edge binary; `rsvg-convert` (librsvg) is the fallback. A
   failed render raises with the renderer's output and leaves no PNG behind, so a PNG you Read is
   always this round's. With no renderer at all, ask the user to install one or give its path; if
   that is not possible, deliver the SVG and say plainly that it was checked by the layout warnings
   only, not looked at.

6. **Embed it** where the ASCII/mermaid/text diagram was, keeping the explanatory text below it:

   ```html
   <p align="center">
     <img src="docs/diagrams/<name>.svg" alt="<one sentence saying what the picture shows>" width="100%">
   </p>
   ```

   Each README language points to its own SVG. The `alt` is a real sentence (screen readers, and
   the text shown if the image fails).

7. **Report** what the picture shows, which files were written, and that it was rendered and
   checked. Commit and push only when the user says so.

## Style rules (what makes it look good)

- **Canvas:** dark diagonal gradient (`#0b1020 → #111a33 → #0f2a2e` or a theme that fits — night
  blues to dawn for a nightly job), faint 24 px grid, soft colour glows behind the main cards,
  a few white sparks kept away from the title. Rounded corners `rx=18`.
- **Title band:** bold 22–23 px title (what this is), 13–14 px subtitle (the one idea in a sentence).
- **Cards:** one palette per role (the client/user warm, the core violet/indigo, the target
  teal/emerald, the output amber); gradient fill, 1.5 px lighter stroke, black drop shadow offset
  (3, 5) at 0.4 opacity; emoji 26–28 px, bold white title 16–18 px, a monospace line for the real
  identifier (package, binary, path), a plain dim line for what it does.
- **Edges:** light arrows for the main direction, dimmer for the reply; monospace label above
  (transport), small dim label below (format). The special path: dashed amber curve with a bold
  amber label. Every arrow gets a marker in its own colour.
- **Badges:** a row of 2–4 translucent pills at the bottom: emoji, bold head, dim one-liner.
- **Text:** short. Labels are 1–5 words; nothing wraps. Identifiers in monospace; prose in the
  system sans. Emoji are fine as icons (they render on GitHub), never inside prose.
- **Language:** one SVG per README language; the same layout, with wording shortened where the
  translation runs long — fix the words, not the layout, so the versions stay alike.

## GitHub constraints

- Shown through `<img>`: no scripts, no `<foreignObject>`, no external fonts or images, no links —
  everything inline in the one file. Use system font stacks (the kit sets them).
- Keep it under ~30 KB; a generated star field or grid pattern is cheap, embedded bitmaps are not.
- The SVG must be well-formed XML (`save()` parses it) — a broken SVG shows as nothing.
- GitHub's light and dark themes both show the picture on its own dark background; do not rely on
  transparency.
